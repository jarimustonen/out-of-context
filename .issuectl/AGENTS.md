# Agents policy (`.issuectl/AGENTS.md`)

Guidance for agents working with this repository's issue tracker. The
generated block at the bottom is rewritten by `issuectl doctor --fix` from
issuectl's built-in schema merged with `issues/.schema.yaml` (and
`.issuectl/transitions.yaml`, if one exists); the prose above it is ours
to maintain. Project-wide guidance lives in the top-level `AGENTS.md`.

## What the tracker is for here

This repository is a one-page static site with a small amount of
long-running work: event changes, design decisions, occasional community
pull requests. The tracker holds the decisions and plans behind that
work, so that a later agent or contributor can find why something is the
way it is. Plans, analyses, and designs belong under the issue they
serve, in the issue's own directory. The repository is public, so an
issue's text, comments, and attachments are public too; write them as
you would a commit message.

## How to work with issues

`issuectl` owns the files under `issues/`. The operational reference is
the `/issue` skill installed in this repo, and the authority on the
current command surface is `issuectl --help` and each subcommand's
`--help`, since the skill text was written for an earlier version of the
binary and the two can disagree. When they do, the binary is right.

Edit issues through the CLI rather than by hand. The reason is what the
CLI does around each write: it takes the repository write lock, validates
frontmatter against the schema, keeps `updated:` and `closed:` correct,
and gives every mutation a version token you can pass back as
`--expected-version` when you want a write to fail if someone else got
there first. A hand edit to frontmatter skips all of that and is the
usual way an issue ends up failing `issuectl doctor`. Body text is
markdown and less fragile, but `issuectl note`, `check`, and `body set`
already cover the common edits and keep the section conventions intact:
running commentary goes under `## Comments`, decisions under
`## Decisions`, and records of agent runs under `## Agent Runs`, which is
where later readers and `issuectl` itself look for them.

Status changes are ordinary updates (`issuectl update --status` or
`issuectl close`). When a change needs a reason, record the reason with
`issuectl note --decision` so the transition and its rationale sit
together. If a `.issuectl/transitions.yaml` is ever added, its rules are
enforced at write time and a refused transition comes back as a
`transition-illegal` error (exit code 2) naming what is missing; read it
rather than retrying with different flags. At the moment this repository
declares no transition rules and no required body sections, as the
generated block below records.

Commits that belong to an issue carry a `Refs-Issue: @<slug>` trailer.
That trailer is what `issuectl sync-commits` and `issuectl changelog`
read to connect history back to issues; `issuectl update --add-commit`
records the same link from the issue side when you want it immediately.

## Before closing

`issuectl doctor` is the check that an issue and its metadata are
consistent; run it before closing and act on anything it reports as
critical. Warnings about legacy layouts and headings are usually fixed by
`issuectl doctor --fix`, which also regenerates the block below. Look at
the diff it produces before committing, because it may touch issues other
than the one you were working on.
